## はじめに：フロントエンドにおける冪等性の落とし穴

Webアプリケーションにおいて、データの整合性を守るための冪等性（Idempotency）の担保は重要です。

特に決済処理やデータ更新などでは、APIの多重リクエストを防ぐために、ボタン押下時にHTMLの `disabled` 属性を付与したり、ローディングオーバーレイでガードをかけるのが一般的なプラクティスです。

しかし実務において、これらのUIによるガードをすり抜け、APIが複数回発火してしまうケースに直面しました。
具体的には、1フレーム未満（十数ミリ秒程度）の間隔で連続入力（マウスのチャタリングを想定）が発生した場合、ローディングオーバーレイをかけているにもかかわらず、2回目の入力が有効として受理されてしまうという現象です。

本記事では、私が調査したブラウザの仕様をもとに、UI制御の限界と、イベントフローを利用したより堅牢な多重発火防止アーキテクチャについて解説します。

## なぜUIガードは数ミリ秒の隙間を許すのか？

結論から言うと、原因はJavaScript上のメモリ更新とブラウザの画面更新の間に存在するタイムラグにあります。

モダンフレームワークを用いた開発では、ボタンクリック時に this.isLoading = true のようなフラグを立ててオーバーレイを表示したり、要素を無効化したりします。このJavaScriptによるメモリ上の状態更新や論理的なDOMツリーの書き換え自体は、メインスレッド上ですぐ（ほぼ0msで）完了します。

一方でJSのメモリ上の値が変わっても、その変更がブラウザ画面にすぐに反映されるわけではありません。ブラウザはDOMの論理的な変更を受け取った後、実際の画面に反映させるためのレンダリングパイプラインを実行する必要があります。

レンダリングパイプラインとは、DOMやCSSの状態をもとに、実際に画面描画されるまでのプロセスのことを指し、各工程を下記のような順番で進みます。

1. Style計算: 変更されたDOM要素に対して、どのCSSが適用されるかを確定させる。
2. Layout計算: 各要素の絶対的な座標（x, y）やサイズをピクセル単位で算出する。
3. Paint / Composite: 描画指示書を作成し、GPUを用いて実際の画面を塗り替える。

DOMが更新された後は、レンダリングパイプラインを経て、その変更が実際に画面に反映されます。
この新しい画面をブラウザはフレームごとに描画しています。1フレームの間隔はディスプレイのリフレッシュレートに依存しており、通常の60Hzであれば、約16.6msごとに画面を描画していることになります。

ボタンを押下できないようにJSから制御をした後も、ユーザーの入力は次のフレームが来るまで古い画面を参照することになります。その結果、オーバーレイが有効に機能するまでに2度目のクリックが受け付けられてしまうということが発生します。

つまりJSでオーバーレイを被せる命令を出してから、実際にボタンクリックが無効になるまでは、最大で16.6ms（1フレーム分）の待ち時間が発生します。

## 解決策：イベントフローのキャプチャ相によるインターセプト

ブラウザの更新ラグを待たずに、極短時間の連続入力を防ぐにはどうすればよいか。
個別のコンポーネントでブロック時間を設けるアプローチもありますが、実装漏れのリスクや、画面遷移時のリスナー管理の煩雑さが残ります。

そこで私が採用したのは、JavaScript標準のイベントフローを利用し、UI（画面）レベルではなくJS（論理）レベルでイベントを破棄するというアプローチです。

### なぜJSレベルなら防げるのか？

前述の通り、画面の更新はブラウザのレンダリングサイクルに依存するため、最大16.6msの遅延が発生します。
しかし、JavaScriptのメインスレッド上で待ち構えるイベントリスナーは、UIの再描画を待つ必要がありません。JS内での命令から同期的に（即座に）処理を挟み込むことが可能です。
UIのガードが間に合わない数ミリ秒の間隔であっても、次に説明するイベントフローの仕組みを利用して、イベントを弾き返すことができます。

### イベントフローとキャプチャ相

DOMイベントは発生した瞬間、以下の3つのフェーズ（イベントフロー）を順番に辿ります。

1. キャプチャ相 (Capturing Phase): DOMの最上位（`window`）から出発し、DOMツリーをターゲットへ向かって降りていく。
2. ターゲット相 (Target Phase): 目的地（クリックされたボタン等）に到達する。
3. バブリング相 (Bubbling Phase): ターゲットから再び最上位へ向かって上っていく。

ReactやVueなどのUIフレームワークにおけるイベントハンドリング（`@click` や `onClick`）や、通常の `addEventListener` は、デフォルトでバブリング相にフックされます。
しかし、バブリング相でイベントを検知した時点では、すでにターゲット相を通過しているため、個別のボタンに紐づいたAPIリクエストなどの本来の処理が発火してしまっています。

そこで、キャプチャ相の利用により、イベントがターゲットに届き、本来起こるはずだったイベント発火の前に、イベントフローを中断させてしまう方法を取ります。
以下は、キャプチャ相でイベントフローを中断する場合のJSの実装例です。

```javascript
// アプリケーションのルートレベル（windowなど）での実装イメージ
let lastClickTime = 0;
const THROTTLE_DELAY = 200; // 意図しない連続入力を弾く閾値（例: 200ms）

window.addEventListener('click', (e) => {
  const currentTime = Date.now();
  if (currentTime - lastClickTime < THROTTLE_DELAY) {
    // イベントの伝播を止め、同要素の他のリスナー実行も即座に差し止める
    e.stopImmediatePropagation();
    e.preventDefault();
    return;
  }
  lastClickTime = currentTime;
}, true); // 第3引数に true を指定し、キャプチャ相でフックする
```

### アーキテクチャとしての利点

このアプローチにより、以下のメリットが得られます。
1. 即時遮断: `stopImmediatePropagation()` を用いることで、個別のボタンに紐づいた本来の処理が発火する前に、イベントそのものを破棄できます。
2. 保守性とメモリ管理: 画面遷移ごとに個別のリスナーを貼ったり剥がしたりする手間が省け、最上位への1回の登録でアプリケーション全域の連続入力イベントを一括でインターセプトできます。これはイベント委譲（Event Delegation）の考え方を応用した広域制御であり、リスナーの削除漏れも減るため、メモリリークの防止にも繋がります。

## まとめ：仕組みを知れば、アプリケーションはもっと堅牢になる

連続入力によるデータの不整合に対して、単にUIガードを入れるといった方法で終わらせず、ブラウザのレンダリングパイプラインやイベントフローのキャプチャ相といった低レイヤーの仕組みに立ち返ることで、より堅牢な仕組みを構築できました。
「なんとなく動く」の裏側にある仕様を理解し、意図通りに制御することが、フロントエンド開発の真の醍醐味だと感じています。
