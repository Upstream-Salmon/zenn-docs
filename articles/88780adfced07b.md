## はじめに：数ミリ秒の隙間を突く「APIの複数回発火」

VueやReactなどのモダンフロントエンド開発において、決済ボタンやフォームの送信時に `disabled` 属性を付与する、あるいはローディングフラグでガードするのは常識です。

しかし、特定の条件下において、**1フレーム（16.6ms）未満の極短時間で連続的なクリックイベントが発生すると、属性ガードをすり抜けてAPIが複数回発火し、バックエンドで予期せぬエラー（データ不整合など）を引き起こす**という事象に遭遇しました。
JS側で即座に状態を更新しているにもかかわらず、なぜ数ミリ秒後の物理的な入力が「有効」として受理されてしまうのか。本記事では、この現象の裏にあるブラウザのレンダリングパイプラインの仕様と、アーキテクチャレベルでの根本的な解決策について解説します。

## なぜ「属性ガード」は貫通されるのか？

結論から言うと、原因は**「JSのメモリ更新」と「ブラウザの物理判定の更新」の間に存在するタイムラグ**にあります[cite: 13]。

ボタンがクリックされた際、JSのマイクロタスクとしてフラグ更新の処理は即座に完了します[cite: 13]。しかし、ブラウザが画面上の「物理的な当たり判定（Hit Test Index）」を無効化するためには、Renderツリーの更新を待たなければなりません[cite: 13]。

ブラウザはディスプレイのリフレッシュレート（通常60Hz）に同期しており、画面の描画（V-Sync）は約16.6ms周期で行われます[cite: 13]。つまり、DOMの変更命令を出してから次の描画タイミングが来るまでの最大16.6ms間、ボタンの当たり判定は「生きている」状態のまま据え置かれます[cite: 13]。
ハードウェア起因の微細なバウンス（連打）などは、まさにこの「ブラウザが次のコマを生成するまでの無防備な隙間」を貫通してしまうのです[cite: 13]。

## 検証における罠： `dispatchEvent` は信用できない

この仮説を検証する際、プログラムから擬似的にクリックを発生させる `dispatchEvent` を用いると、1ms間隔でも防げる（イベントが重複しない）という結果が出ることがあります。
しかし、これは罠です。`dispatchEvent` によるイベント発火は、ブラウザの物理的なレンダリングサイクル（V-Sync待ち）をバイパスして直接タスクキューに積まれてしまうため、純粋な物理的連続入力の再現には不適切です[cite: 13]。
このブラウザの実行エンジンの仕様差を理解しておくことが、本質的な対策への第一歩となります[cite: 13]。

## 解決策：イベントフローの「キャプチャ相」によるインターセプト

ブラウザの物理的な更新ラグ（16.6ms）を待たずに、極短時間の連続入力を根本から防ぐにはどうすればよいか。
個別のコンポーネントで閾値を設けて防ぐアプローチもありますが、それでは実装漏れやコンポーネント単位のバグを引き起こしかねません。

そこで、JavaScriptの**「イベントフロー」**の原則に立ち返りました。イベントはDOMツリーの最上位（`window`）から出発し、ターゲットへ降りていく「キャプチャ相」、ターゲットへ到達する「ターゲット相」、そして再び最上位へ戻る「バブリング相」の3つのフェーズを辿ります。
通常の `addEventListener` はバブリング相で実行されますが、これではターゲットの処理が動いてしまいます[cite: 12]。

確実な防衛策は、**ターゲットにイベントが届く前の「キャプチャ相」で先回りして捕まえ、閾値以下の連続入力であればその場で破棄する**ことです[cite: 12]。

```javascript
// アプリケーションのルートレベル（windowなど）での実装イメージ
let lastClickTime = 0;
const THROTTLE_DELAY = 200; // 意図しない連続入力を弾く閾値（例: 200ms）

window.addEventListener('click', (e) => {
  const currentTime = Date.now();
  if (currentTime - lastClickTime < THROTTLE_DELAY) {
    // イベントの伝播を止め、同要素の他のリスナー実行も即座に差し止める
    e.stopImmediatePropagation();
    e.preventDefault();
    return;
  }
  lastClickTime = currentTime;
}, true); // 第3引数に true を指定し、キャプチャ相でフックする
```

### アーキテクチャとしての利点

このアプローチにより、以下のメリットが得られます。
1. **即時遮断:** `stopImmediatePropagation()` を用いることで、個別のボタンに紐づいた本来の処理が発火する前に、イベントそのものを完全に抹殺できます[cite: 12]。
2. **保守性とメモリ管理:** 画面遷移ごとに個別のリスナーを貼ったり剥がしたりする手間が省け、最上位への1回の登録でダイアログ等を含めたアプリケーション全域の連続入力イベントを一括でインターセプトできます。これはメモリリークの防止にも繋がります。

## まとめ：仕組みを知れば、アプリケーションはもっと堅牢になる

連続入力によるデータの不整合に対して、単に「フラグを立てる」といった対症療法で終わらせず、ブラウザのレンダリングパイプライン（V-Sync）やイベントフローのキャプチャ相といった低レイヤーの仕組みに立ち返ることで、より堅牢なアーキテクチャを構築できました[cite: 13]。
「なんとなく動く」の裏側にある仕様を理解し、意図通りに制御することが、フロントエンド開発の真の醍醐味だと感じています。
