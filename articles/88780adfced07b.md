旧版では「DOMにオーバーレイを追加しても、次のフレームが描画されるまで（最大16.6ms）はクリックが下の要素に届く」と説明していましたが、この説明は誤りでした。仕様を読み、実験で確かめ直した結果を、訂正としてまとめます。

## 結論

- クリックの処理の中で、オーバーレイの追加や `disabled` の設定を**同期的に**行えば、**描画を待たずに**、次のクリックから効きます。
- ガードがすり抜けるのは、ガードを立てるのが**タスクの待ちの後**になったとき、またはガードを**早く外しすぎた**ときです。
- `element.click()` で連打を再現しても、オーバーレイの効果は確かめられません。当たり判定を通らないからです。

## きっかけ

実務で、ボタンの連打（約10ms間隔。マウスのチャタリングを想定）により、同じリクエストが2回送られる事象がありました。

当時、私は「DOMを変えても、画面に描画されるまではクリックの判定に反映されない。だから1フレーム未満の連打はオーバーレイをすり抜ける」と考え、`element.click()` を10ms間隔で2回呼ぶスクリプトで再現できたことを根拠にしていました。

後からこの説明に疑問を持ち、仕様を読み直して実験したところ、説明も検証方法も誤っていたことが分かりました。

## 前提1：当たり判定は「描画された絵」ではなくDOMとレイアウトで行われる

クリックされた位置にどの要素があるかを決める処理を、当たり判定（hit testing）と呼びます。CSSOM Viewの仕様では、`elementFromPoint()` が返す要素は当たり判定で決まると定義され、その詳細は将来のCSSやHTMLで定める、とされています（[CSSOM View](https://drafts.csswg.org/cssom-view/#dom-document-elementfrompoint)）。

ポイントは、当たり判定が見ているのは「画面に塗られたピクセル」ではなく、DOMとレイアウトだということです。DOMに要素を追加すれば、次の入力の当たり判定はその新しいDOMで行われます。描画（Paint）を待つ必要はありません。

なお、`opacity: 0` の透明な要素も当たり判定の対象です。見えない覆いでもクリックは止まります。

## 前提2：イベントループのタスクとマイクロタスク

- 2回目のクリックは、独立した**タスク**として順番を待ちます。
- `Promise.then` や `await` の再開、Vueの `$nextTick` などの**マイクロタスク**は、今のタスクが終わった直後、次のタスクより前にすべて実行されます。

つまり、1回目のクリックの処理の中（またはその直後のマイクロタスク）でオーバーレイを追加すれば、2回目のクリックより先に必ずDOMに入ります。

逆に、`setTimeout`、`requestAnimationFrame`、通信の応答待ちなど、**タスクの待ち**を挟んでからオーバーレイを追加すると、その間に2回目のクリックが割り込めます。

## 実験

### 対象のページ

送信の回数を数えるだけのページです。クリックの処理の中で、画面を覆うdivを追加するかどうか、追加を遅らせるかどうかを切り替えられるようにしました。

```html
<button id="submit">送信</button>
<p id="count">0</p>
<script>
  const USE_COVER = true;   // false: 覆いなし（対照）
  const COVER_DELAY = -1;   // -1: すぐ追加 / 0以上: その時間だけ遅らせて追加

  const btn = document.getElementById('submit');
  const countP = document.getElementById('count');
  let count = 0;
  window.count = 0;

  btn.addEventListener('click', () => {
    count++;
    countP.textContent = count;
    window.count = count;

    if (USE_COVER) {
      const addCover = () => {
        const cover = document.createElement('div');
        cover.style.position = 'fixed';
        cover.style.inset = '0';
        cover.style.background = 'rgba(0,0,0,0.3)';
        document.body.appendChild(cover);
        setTimeout(() => cover.remove(), 1500);
      };
      if (COVER_DELAY < 0) addCover();
      else setTimeout(addCover, COVER_DELAY);
    }
  });
</script>
```

### 操作役のスクリプト

Playwrightの `page.mouse` は、要素ではなく**座標**を押します。ブラウザはその座標に何があるかを当たり判定で決めるので、上に覆いがあればクリックは覆いに当たります。

```javascript
import { chromium } from 'playwright';
import path from 'node:path';
import { fileURLToPath } from 'node:url';

const here = path.dirname(fileURLToPath(import.meta.url));
const browser = await chromium.launch({ headless: false });
const page = await browser.newPage();
await page.goto('file://' + path.join(here, 'mini.html'));

const box = await page.locator('#submit').boundingBox();
const x = box.x + box.width / 2;
const y = box.y + box.height / 2;

await page.mouse.move(x, y);
await page.mouse.down();
await page.mouse.up();
await page.waitForTimeout(10);   // 約10ms後に2回目
await page.mouse.down();
await page.mouse.up();

await page.waitForTimeout(2000);
console.log('送信の回数:', await page.evaluate(() => window.count));
await browser.close();
```

### 結果

Playwright同梱のChromium（2026年10月時点）で実行しました。指定した間隔に対して、実際のクリック間隔は処理の都合で数ms〜十数msずれます。

| パターン        | 設定                               | 送信回数               |
| --------------- | ---------------------------------- | ---------------------- |
| 対照            | 覆いなし                           | 2                      |
| すぐ追加        | クリックの処理の中で `appendChild` | 1                      |
| 遅らせて追加    | `setTimeout(addCover, 50)`         | 2                      |
| 0ms遅らせて追加 | `setTimeout(addCover, 0)`          | 実行のたびに1と2が混在 |

- 覆いをクリックの処理の中で追加すれば、1フレーム未満の2回目のクリックも止まりました。
- 追加をタスクとして遅らせると、2回目のクリックが先に処理されて通りました。
- 0msでも、覆いを追加するタスクと2回目のクリックのタスクの、どちらが先に実行されるかが毎回変わりました。HTMLの仕様は、複数のタスクの待ち行列のどれを次に処理するかを実装に任せています。**タスクを一つ挟むだけで、結果が実行のたびに変わる競合になる**ということです。

### element.click() では確かめられない

同じページで、`element.click()` を使って2回クリックすると、覆いを同期的に追加していても、10ms間隔でも1秒間隔でも2回送られました。

HTMLの仕様では、`click()` は無効化されたフォーム部品でなければ、その要素に対して直接クリックを発生させます（[HTML Standard](https://html.spec.whatwg.org/multipage/interaction.html#dom-click)）。座標から要素を探す当たり判定を通らないので、上に何が重なっていても届きます。`dispatchEvent` も同様です。

私の当時の検証は、この方法で「すり抜けを再現できた」と判断していました。実際には、描画のラグがあってもなくても同じ結果になる方法で、何も確かめられていなかったことになります。

### キーボードの入力は覆いを迂回する

同じページで、ボタンをマウスでクリックした直後、覆いが出ている間にEnterキーを押すと、送信がもう1回実行されました。

キーボードの入力は座標を持たず、フォーカスのある要素に届きます。マウスで押した時点でフォーカスはボタンに移っていて、フォーカスのあるボタンでEnterやSpaceを押すと、ブラウザはそのボタンにclickイベントを発生させます。当たり判定を一度も通らないので、上に何が重なっていても関係ありません。

逆に言えば、clickの処理の中に置いたフラグや `disabled` なら、キーボードの入力も同じように止められます。

## では、UIのガードはどんなときにすり抜けるのか

実験と前提から、次のような作りがすり抜けの原因になりえます。

- **ガードを立てるのがタスクの待ちの後**：入力チェックや確認の結果を待ってから、あるいは通信の応答を待ってからオーバーレイを出す
- **ガードを早く外しすぎる**：二重押し防止のフラグを、通信の完了ではなく次のマイクロタスク（`$nextTick` など）で戻すと、次のクリックの時点では必ず外れています
- **覆いだけに頼る**：覆いが止めるのはポインターの入力だけです。フォーカスがボタンに残っていれば、Enterキーで押せてしまいます

## 対策の整理

| 対策                                                             | 守れるもの                                               | 注意点                                                               |
| ---------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------- |
| クリックの処理の中で同期的にガードを立て、通信の完了まで外さない | 通信中の重複クリック（間隔を問わない）                   | 部品の使い方次第で効かなくならないよう、誤用できない作りにする       |
| 最初のクリックから一定時間、後続を無視する（スロットリング）     | チャタリングなど短い間隔の連打                           | 処理時間は毎回違うのに時間は固定。一定時間を過ぎた入力は通す         |
| サーバー側の冪等キー                                             | 画面をすり抜けた重複（再送、別タブ、キーボード経路など） | クライアントが操作ごとにキーを作り、サーバーで一意制約などで見分ける |

画面のガードは、入口がいくつあっても必ず通る場所に置きます。ボタンを押す経路ならclickの処理の中です。テキスト欄でEnterを押したら送信する、といった別の入口があるなら、最終的に通信を呼ぶ関数の入口に置きます。

画面のガードは利用者の体験を守るもの、データの整合性はサーバー側で守るもの、と役割を分けて考えるのが安全です。旧版のタイトルにあった「冪等性」は、本来サーバー側の性質（同じ操作が2回届いても結果が1回と同じになる）を指す言葉で、画面のガードとは別物でした。

## まとめ

- DOMの変更は同期的に行われ、次のクリックの当たり判定は描画を待たずに新しいDOMで行われる
- UIのガードがすり抜けるのは、ガードを立てるのが遅いか、外すのが早いとき
- 覆いはキーボードの入力を止めない。ガードは見た目の覆いではなく、処理の入口に置く
- 連打の検証には、当たり判定を通る入力（座標へのマウス操作）を使う

当初の説明は、AIの説明をそのまま信じて書いたものでした。仕様を読み、自分で対照を置いて実験したことで、誤りに気づけました。「なんとなくそれらしい説明」こそ、一次資料と実験で確かめる価値があると感じています。
